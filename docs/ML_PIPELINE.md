# Categorization & ML Pipeline

## Two categorizers, one default

The app has two independent ways to assign a category, defined in
`app/classification/`:

1. **Rule-based (`rules.py`)** — the default. A merchant-name lookup
   table, then a keyword-in-text lookup table, checked in that order.
2. **ML classifier (`ml_classifier.py`)** — TF-IDF + Logistic Regression,
   trained on a small synthetic dataset. Shown as a secondary
   *suggestion* next to the rule-based result (see the upload page); it
   never overrides the rule-based category on its own.

### Why rule-based is the default, not the ML model

This is a deliberate choice, not a placeholder until "real" ML gets
added:

- **Transparency.** A user (or an interviewer) can look at
  `MERCHANT_CATEGORY` and `KEYWORD_CATEGORY` in `rules.py` and know
  exactly why a transaction got categorized a certain way. A logistic
  regression's decision, while inspectable in principle (via its learned
  coefficients), isn't something a end user can reason about from the UI.
- **No training data required, and no risk of overfitting to it.** The
  rules work correctly for any merchant they cover, on day one, with zero
  examples. The ML model's accuracy is bounded by both the size and the
  realism of its training set — see the honesty section below.
- **Financial data deserves the more predictable default.** A spending
  dashboard that mis-categorizes silently is worse than one that defaults
  a genuinely unrecognized merchant to "Other" and asks the user to pick
  a category — which is exactly what the rule-based path does when
  neither table matches.

The ML classifier still exists and is fully wired up (`categorize()` in
`categorize.py` calls both and returns both results) because comparing a
transparent baseline against a trained classifier — and being honest
about which one is more trustworthy and why — is itself the more
defensible engineering story for this project than only shipping one.

## The dataset

`scripts/generate_training_data.py` generates `data/training_data.csv`:
240 rows (20 per category × 12 categories), each a short templated
snippet combining a merchant name, an item/description phrase, and a
total-amount phrase — built to resemble what cleaned OCR text for that
category tends to contain (see `CATEGORY_TEMPLATES` in that script for
the exact templates and merchant/phrase pools).

**This is synthetic data, generated by a fixed-seed random combination of
templates — not real receipts, and not a large corpus.** No real
transaction data was available or appropriate to use for a project like
this, so the honest choice was to generate a small labeled set and be
upfront about what that does and doesn't prove.

## Model and training process

- **Features**: TF-IDF over the raw text, unigrams + bigrams
  (`TfidfVectorizer(ngram_range=(1,2))`).
- **Model**: `LogisticRegression(max_iter=1000)`. Naive Bayes was also
  tried during development (`MultinomialNB`) and scored within ~1-2
  points of logistic regression on the same split — logistic regression
  was kept as the slightly stronger and equally interpretable option. A
  neural network was not tried: with ~240 short synthetic examples, a
  model with that much capacity would memorize the templates rather than
  learn anything that generalizes, and its decisions would be strictly
  harder to inspect than logistic regression's per-feature weights.
- **Training/evaluation**: `train_test_split(test_size=0.25, stratify=labels,
  random_state=42)` — a genuine held-out test set, not training accuracy.
  `scripts/train_classifier.py` runs this, saves the fitted pipeline to
  `data/classifier_model.pkl`, and writes the measured metrics to
  `docs/ML_METRICS.md`.

## Results — read `docs/ML_METRICS.md`, not this file, for the numbers

`docs/ML_METRICS.md` is generated by the training script and contains the
actual accuracy/precision/recall/F1/confusion matrix from the most recent
run — not estimates written by hand. Re-run
`python scripts/train_classifier.py` to reproduce it (the split is
deterministic).

**Why the numbers are high, and why that's not the point.** The synthetic
categories were generated from fairly distinct vocabulary pools by
construction (e.g. "Food" templates always include words like "Biryani"
or "Pizza"; "Utilities" templates always include "electricity bill" or
"broadband"). A classifier finds those patterns easily. That says the
model can distinguish these 12 *template families* — it does not say the
model would reliably categorize a messy, real, OCR'd receipt for a
merchant it has never seen described in an unfamiliar way. Treat the
metrics file as evidence the pipeline works end-to-end (data generation
-> training -> evaluation -> a saved, loadable model), not as a
production accuracy claim.

## Historical corrections as a future signal

The schema doesn't have a separate "corrections" table, but every edit
made on the verification screen or the transaction table already updates
the `category` column directly via `app/database/repository.py`. Those
edited, confirmed rows are real labeled examples of what the user
actually wants — retraining `scripts/train_classifier.py` against
`SELECT raw_text, category FROM transactions WHERE confirmation_status='confirmed'`
instead of the synthetic CSV is the natural next step once there's enough
real confirmed history to be worth it (see `docs/LIMITATIONS.md` /
Future Improvements). It wasn't built because there's no real usage
history yet to train on — building it now would mean training on the
same synthetic seed data twice.
